# 0002 — `vls`, a verified replacement for `ls`

## Intent

A small, predictable `ls` I can trust. Running `vls [-a] [-r] [PATH...]` lists
directory contents one entry per line, sorted by raw bytes like `LC_ALL=C ls`.
Every entry is exactly one line, so output can be machine-processed safely,
even for hostile file names. Everything `vls` prints and its exit status are
decided by verified code. The only trusted code is a thin shell that asks
the OS for facts and prints the result.

## Architecture

```
argv ──▶ [trusted shell] parse flags, stat operands, read_dir
              │  Request { all, reverse, operands: [(name, Missing(msg) | Unreadable(msg) | File | Dir([entry names]))] }
              ▼
         [verified core]  pure function, fully specified
              │  Response { stdout: [line], stderr: [line], exit: 0 | 2 }
              ▼
         [trusted shell] write lines (each + "\n"), exit
```

- Names are **byte strings** (no UTF-8 assumption) everywhere.
- The shell is written in the vericode stage and reviewed in that PR (it is
  not hash-locked). It must contain no listing logic: no sorting, filtering,
  escaping or formatting.

## Interface

- Binary: `vls` (crate `ls`, `katas/0002-ls`). Does not shadow system `ls`.
- Verified core: `fn run(req: &Request) -> Response` (exact Rust types are
  fixed in the spec stage).

## Decisions

| #   | Question | Decision | Spec clause |
|-----|----------|----------|-------------|
| D1  | Scope? | Flags `-a` and `-r` only. No `-A`, `-l`, `-t`, `-S`, columns, colour, long options, `--help`. | Request type |
| D2  | Proved vs trusted? | Verified core decides all stdout lines, stderr lines and the exit code. The shell only parses argv, queries the OS, and prints. | `run` ensures |
| D3  | Who writes the shell? | Agent, in the vericode stage, reviewed in the PR; not locked. | — (review) |
| D4  | Name representation & order? | Raw bytes; sort lexicographically by byte (shorter prefix first), on the raw name **before** escaping. | `sorted_bytewise` |
| D5  | `-a`? | Show entries starting with `.`, and add `.` and `..` to every listed directory. Without `-a`, entries starting with `.` are hidden. | dir-group entries |
| D6  | `.`/`..` position? | Sorted as ordinary names (`!x` < `.` < `..` < `.h` < `a`), also under `-r`. | D4 applies |
| D7  | `-r`? | Reverses every ordering: entries within each directory, the file-operand group, and the order of directory groups. | `rev` variants |
| D8  | No operand? | Shell substitutes the single operand `.`. | — (shell) |
| D9  | Operand classification? | Shell uses `metadata()` (follows symlinks): missing → `Missing(msg)`, directory that can't be read → `Unreadable(msg)`, directory → `Dir(entries)`, anything else → `File`. Entries inside directories are names only, never stat'd. | — (shell) |
| D10 | Robust core? | No preconditions on the Request. Within a directory, the core drops entries that are empty, `.` or `..` (re-adding `.`/`..` only for `-a`) and collapses duplicates. | dir-group entries |
| D11 | Output form? | One line per entry; each line is the **escaped** name (D12). No columns, no colour, no quoting. | `escape` |
| D12 | Escaping? | Byte by byte: `\` → `\\`; LF → `\n`; TAB → `\t`; other bytes 0x20–0x7E unchanged; every other byte → `\x` + 2 lowercase hex digits. E.g. `café` prints as `caf\xc3\xa9`. | `escape` |
| D13 | File operands? | Printed as typed (`d/f` stays `d/f`), escaped. Dotfile hiding never applies to operands. All file operands form **one** group, sorted per D4/D7, printed first. | file group |
| D14 | Directory operands? | Each forms one group, groups ordered by operand name per D4/D7. Equal names keep argument order, also under `-r`. Duplicate operands are listed again. | dir groups |
| D15 | Headers? | Each directory group starts with `NAME:` (escaped) iff 2 or more operands were given, counting missing/unreadable ones. | header rule |
| D16 | Separators? | Exactly one empty line between two consecutive printed groups; none before the first or after the last. An empty directory is still a group (its header alone, if headers are on). | layout |
| D17 | Errors? | For each Missing/Unreadable operand, in **argument order**, one stderr line: `vls: cannot access NAME: MSG` / `vls: cannot open directory NAME: MSG`, with NAME and MSG escaped. These operands produce no stdout group. Other operands are still listed. | stderr |
| D18 | Exit status? | 0 if no operand failed, else 2. | exit |
| D19 | Argv parsing? | GNU-ish: clustered short flags (`-ar`), flags anywhere among operands, `--` ends flags, a lone `-` is an operand. Unknown flag → `vls: invalid option -- 'X'` + usage line on stderr, exit 2, nothing listed. | — (shell) |
| D20 | Totality? | The core terminates and never panics, for every Request. | Verus total correctness |

## Examples

Directory `d1` holds `b`, `a`, `.h`, `!x`. `d2` holds `z`. `d3` is empty. `f1` and
`.hid` are regular files. `missing` doesn't exist.

| #   | Command | Expected stdout (⏎ = newline) / stderr / exit | Plausible wrong answer the spec must reject |
|-----|---------|-----------------------------------------------|---------------------------------------------|
| E1  | `vls d1` | `!x⏎a⏎b⏎`, exit 0 | `a⏎b⏎!x⏎` (alphabetic, not bytewise); including `.h` |
| E2  | `vls -a d1` | `!x⏎.⏎..⏎.h⏎a⏎b⏎` | `.⏎..⏎!x⏎.h⏎a⏎b⏎` (dots forced first) |
| E3  | `vls -ar d1` | `b⏎a⏎.h⏎..⏎.⏎!x⏎` | `.` and `..` left unreversed |
| E4  | `vls -r d1 d2 f1` | `f1⏎⏎d2:⏎z⏎⏎d1:⏎b⏎a⏎!x⏎` | dir groups in argument order; file group last |
| E5  | `vls f1 .hid d2 d3` | `.hid⏎f1⏎⏎d2:⏎z⏎⏎d3:⏎` | `.hid` hidden; no header for empty `d3`; trailing blank line |
| E6  | `vls d1 missing` | stdout `d1:⏎!x⏎a⏎b⏎`; stderr `vls: cannot access missing: No such file or directory⏎`; exit 2 | no `d1:` header (missing operand not counted); exit 0 |
| E7  | `vls missing` | stdout empty; one stderr line; exit 2 | exit 0 |
| E8  | `vls d1 d1` | `d1:⏎!x⏎a⏎b⏎⏎d1:⏎!x⏎a⏎b⏎` | listed once |
| E9  | dir with entry names `a⏎b`, `back\slash`, `café` | `a\nb⏎back\\slash⏎caf\xc3\xa9⏎` | a raw newline inside an entry; `\` left unescaped (then `a⏎b` and a name literally spelled `a\nb` print the same line) |
| E10 | core gets entries `["a","a",".","","b"]`, no `-a` | `a⏎b⏎` | `a` twice; an empty line |
| E11 | `vls -x d1` | stderr: invalid option + usage; stdout empty; exit 2 | listing `d1` anyway |

(E6/E7 message text comes from the OS via the shell; the spec fixes only the
format around it.)

## Properties

- P1 **Escaping is injective**: distinct names never produce the same line.
- P2 **Escaped lines are safe**: they consist only of printable ASCII
  (0x20–0x7E), so they never contain a newline or control byte.
- P3 **Faithful listing**: a directory group's entry lines are exactly the
  escaped D10/D5-filtered entry set, with each name once, in strictly
  increasing byte order (strictly decreasing with `-r`).
- P4 **Reverse is reverse**: for any directory, its entry lines under `-r`
  are the exact reverse of the lines without `-r`. (Proved for directory
  listings. For the file group, which may contain duplicates, `-r` is checked
  by example E4 only; decided in spec review.)
- P5 **Errors ⇔ exit 2**: the exit code is 2 iff stderr is non-empty.
- P6 **Determinism**: the core is a pure function (implied by `run` being
  specified as an exact function of the Request).

## Not verified

- The trusted shell: argv parsing (D19), the `.` default (D8), operand
  classification (D9), reading directories, writing bytes, and OS error
  texts. Covered by: shell has no listing logic (review), runtime tests, and a
  **differential test**: `cargo test` builds a temp dir of plain-ASCII names
  and checks `vls` stdout equals `LC_ALL=C ls -1` for `""`, `-a`, `-r`, `-ar`,
  several operands, missing operands, and empty dirs. Skipped if GNU `ls`
  isn't installed.
- Performance and memory for huge directories: by review.
- Deliberate differences from GNU `ls`: the escaping style (D12), unquoted
  names and the `vls:` prefix in errors (D17), no locale collation (D4), no
  `-A` (D1).
